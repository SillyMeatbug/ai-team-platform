# Архитектура системы «AI Team Platform» / LLM Aggregator

Документ описывает решение с позиции **системного анализа**: назначение, границы системы, состав функциональных блоков, интеграции, развёртывание и ключевые потоки данных. Технический стек указан там, где это влияет на границы ответственности и контракты.

---

## 1. Назначение и бизнес-контекст

### 1.1. Продуктовая цель

Платформа позволяет пользователю:

- создавать **проекты** как контексты совместной работы;
- подключать к проекту **AI-агентов** из общей библиотеки ролей;
- загружать **файлы** (брифы, материалы);
- вести **групповой чат** с участием нескольких агентов и оркестрацией ответов;
- для проектов с флагом «crypto» использовать дополнительный функционал (**paper trading**, рыночный контекст) — при включённой конфигурации.

Отдельная подсистема API реализует **агрегацию ответов нескольких LLM-маршрутов** (analyst / critic / arbiter) по конфигурации `routes.yaml` — это «ядро» LLM Aggregator в текущем каркасе (реальные провайдерские вызовы дорабатываются по правилам репозитория).

### 1.2. Заинтересованные стороны

| Стейкхолдер | Интерес |
|-------------|---------|
| Конечный пользователь | Работа через веб-интерфейс: проекты, чат, файлы, результаты |
| Оператор / DevOps | Деплой на Railway, переменные окружения, доступность API и БД |
| Разработчик | Расширение роутеров, оркестратора, интеграция реальных LLM (STEP 2+) |
| Внешний провайдер LLM (OpenRouter) | Исходящие HTTPS-запросы с ключом и заголовками идентификации |

## 2. Границы системы (System Context)

```
                    ┌─────────────────────────────────────────┐
                    │           Пользователь (браузер)          │
                    └───────────────────┬─────────────────────┘
                                        │ HTTPS
                                        ▼
                    ┌─────────────────────────────────────────┐
                    │   Frontend (Next.js, SSR/CSR, Railway)     │
                    │   Публичный URL *.up.railway.app           │
                    └───────────────────┬─────────────────────┘
                                        │ REST / JSON / fetch (CORS)
                                        ▼
                    ┌─────────────────────────────────────────┐
                    │   Backend API (FastAPI, Uvicorn, Railway)  │
                    │   Префиксы: /, /docs, /v1/…               │
                    └───────┬─────────────────────┬─────────────┘
                            │                     │
              ┌─────────────▼─────────┐   ┌──────▼──────────────────┐
              │ PostgreSQL (Railway)  │   │ OpenRouter HTTPS API     │
              │ DATABASE_URL          │   │ (AGGREGATE_MOCK / ключ)   │
              └─────────────────────┘   └──────────────────────────┘
```

**Вне системы (по умолчанию):** корпоративный IdP, очереди сообщений, отдельный CDN для статики (кроме встроенной раздачи Next), мониторинг SaaS — не обязательны для минимального контура.

## 3. Логическая архитектура (контейнеры и ответственность)

### 3.1. Frontend (`frontend/`)

| Аспект | Описание |
|--------|----------|
| Роль | SPA/SSR-приложение: дашборд проектов, карточки, мастер создания проекта, страница проекта с чатом, вкладки (в т.ч. paper trading для crypto-проектов) |
| Стек | Next.js (App Router), React 19, TypeScript, Tailwind, компоненты UI (Radix/shadcn-подобные), i18n (EN/RU) |
| Вызовы API | Единая точка — `frontend/lib/api.ts`: базовый URL из `getApiBaseUrl()` (env + атрибут `data-api-public-url` на `<html>` для продакшена на Railway) |
| Сборка prod | `output: 'standalone'`, Docker multi-stage: статика и `public` копируются в дерево standalone для корректных путей `/_next/static` |
| Наблюдаемость | Vercel Analytics подключается только при `VERCEL=1` |

### 3.2. Backend API (корень репо + `app/`)

| Аспект | Описание |
|--------|----------|
| Роль | REST API домена платформы + endpoint агрегации LLM |
| Точка входа | `main.py`: создание `FastAPI`, CORS, подключение роутеров |
| Конфигурация | `app/config/loader.py`: Pydantic Settings, `.env` в корне проекта, путь к `routes.yaml` |
| Состояние приложения | `app.state`: httpx-клиент (единый на приложение), настройки, кэш агрегации, лимиты бюджета, файловое хранилище, метрики |

#### Основные HTTP-модули (роутеры)

| Префикс / модуль | Назначение |
|------------------|------------|
| `GET /` | Служебный health-подобный ответ |
| `/docs` | OpenAPI (Swagger) |
| `/v1` (`app/api/router.py`) | Агрегация LLM по маршрутам из `routes.yaml`, кэш, бюджет, заголовок-заглушка 429 |
| `/v1` (`projects_router`, `files_router`, `agent_library_router`, `chat_router`) | CRUD проектов, агенты проекта, файлы, библиотека агентов, чат/оркестрация |
| `/v1/market` | Рыночные данные и связанная логика (контекст для crypto-флоу) |
| metrics | Служебные метрики |

### 3.3. Хранилище данных (PostgreSQL)

| Аспект | Описание |
|--------|----------|
| ORM | SQLAlchemy 2.0 async, модели в `app/models/database.py` |
| Сущности (укрупнённо) | `Agent`, `AgentLibraryFile`, `Project`, связи проект–агент, `ProjectFile`, `ChatMessage`, дебаты/результаты, `PaperTrade` и др. |
| Инициализация | `init_db` + идемпотентный `seed_agents` в lifespan |

### 3.4. Файловое хранилище

| Аспект | Описание |
|--------|----------|
| Реализация | `app/core/storage.py` (`FileStorage`), каталог из настроек (`UPLOAD_DIR`) |
| Использование | Загрузки проектов, файлы библиотеки агентов |

### 3.5. Конфигурация маршрутов LLM (`routes.yaml`)

| Аспект | Описание |
|--------|----------|
| Роль | Декларативное описание провайдера, модели, роли (analyst/critic/arbiter), системных промптов |
| Загрузка | При старте приложения; ошибка загрузки блокирует подъём сервиса |
| Валидация | По правилам репозитория — при старте |

## 4. Ключевые потоки данных (Use Cases)

### 4.1. Локальная разработка vs продакшен

- **Локально:** фронт обычно `127.0.0.1:3000`, бэк `127.0.0.1:8000`; CORS включает локальные origins по умолчанию + `CORS_ALLOWED_ORIGINS`.
- **Railway:** фронт и бэк — разные публичные HTTPS-домены; фронт должен знать базовый URL API (`NEXT_PUBLIC_API_URL` при сборке и/или `BACKEND_PUBLIC_URL` на runtime для подстановки в HTML); бэк должен разрешать origin фронта в `CORS_ALLOWED_ORIGINS`.

### 4.2. Создание проекта и список проектов

1. Пользователь на фронте открывает дашборд → `GET /v1/projects`.
2. Создание → `POST /v1/projects`, затем назначение агентов и загрузки файлов соответствующими вызовами API.

### 4.3. Чат и оркестрация

1. Клиент отправляет сообщения/получает историю через endpoints чата (`chat_router` + сервис оркестрации).
2. `DiscussionOrchestrator` координирует раунды, агентов и вызовы к LLM-слою согласно политикам проекта и ролей.

### 4.4. Агрегация `/v1/aggregate` (ядро Aggregator)

1. Запрос с телом и параметрами ролей.
2. Отбор активных маршрутов из `routes.yaml`.
3. Диспетчер (`dispatcher`) при `AGGREGATE_MOCK=true` использует моки; иначе — исходящие запросы через общий `httpx.AsyncClient` из `app.state`.
4. Учёт бюджета, кэша ответов, метрик; формирование объединённого результата и статуса (success/partial/failed).

### 4.5. Crypto / Paper trading

- При `is_crypto_enabled` у проекта включается UI и API paper trading.
- Запросы идут к соответствующим endpoints; при отключении crypto возможен редирект/ограничение на уровне страницы.

## 5. Нефункциональные требования и ограничения

### 5.1. Безопасность и конфиденциальность

- По правилам репозитория: в логах не должны попадать полный текст запросов пользователя, API-ключи, полные payloads — допускаются `request_id`, маршруты, статусы, метрики.
- Секреты только через переменные окружения (Railway Variables / `.env` локально).

### 5.2. Надёжность

- Один экземпляр httpx-клиента на приложение (lifespan), без создания клиента внутри хендлеров.
- Идемпотентный seed агентов при старте.

### 5.3. Ограничения текущей версии (каркас)

- Реальная интеграция всех провайдеров LLM и полная продуктовая политика могут быть помечены как **STEP 2+** в коде (см. `.cursorrules`).
- Горячая перезагрузка `routes.yaml` без рестарта не заявлена.

## 6. Развёртывание (Railway) — логическая модель

| Сервис Railway | Образ / сборка | Критичные переменные |
|----------------|----------------|----------------------|
| **Backend** | Dockerfile в `backend/` (или корневой контекст по настройке), Uvicorn `0.0.0.0`, порт `PORT` | `DATABASE_URL` (рекомендуется `postgresql+asyncpg://`), `OPENROUTER_*`, `AGGREGATE_MOCK`, `CORS_ALLOWED_ORIGINS`, пути загрузок и лимиты чата при необходимости |
| **Frontend** | Dockerfile в `frontend/`, Next standalone | `NEXT_PUBLIC_API_URL` и/или `BACKEND_PUBLIC_URL` (HTTPS бэкенда), без секретов БД на сервисе фронта |
| **Postgres** | Managed | `DATABASE_URL` выдаётся сервисом БД; на бэкенд передаётся через **Variable Reference** |

Рекомендация: не дублировать переменные бэкенда на сервисе фронта (`DATABASE_URL`, `OPENROUTER_*` и т.д.) — это не используется клиентским приложением и усложняет сопровождение.

## 8. Глоссарий

| Термин | Значение |
|--------|----------|
| **Aggregator** | Режим объединения ответов нескольких LLM-маршрутов по ролям |
| **Route** | Запись в `routes.yaml`: провайдер, модель, роль, промпт |
| **Agent (БД)** | Сущность библиотеки агентов платформы, привязывается к проектам |
| **Paper trading** | Учебные сделки/статусы для crypto-проектов |
| **Standalone (Next)** | Режим сборки для минимального Node-сервера в Docker |
